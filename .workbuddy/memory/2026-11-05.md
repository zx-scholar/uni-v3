## 请求签名体系对比（老项目 xports-view-client vs 本项目）

- 老项目 `E:\AcodeStorage\xports-view-client\src\api\request.js`（axios + `md5` + lodash）与本项目 `src/utils/request.js` + `src/utils/crypto.js`（uni.request + `js-md5`）是**同一套 MD5 sign 签名协议**：apiKey/timestamp/channelId + 业务参数 → key 升序拼 `k=v` → `url + 拼串 + apiSecret` → encodeURIComponent（额外转义 `( ) ' ! ~`）→ md5 得 sign。
- 不是请求体加密，只是签名；apiKey/apiSecret 明文在客户端，只能防篡改 + 弱防重放。
- 已确认结论：本项目**可以直接对接老项目后端**，无需改签名实现（用户明确不需要兼容 key 大小写排序、undefined 归一差异）。
- 差异仅工程层：axios vs uni.request、Toast 并发 vs loading 计数、401 处理、Authorization 头（老项目无 token，靠 netUserId 参数）、老项目自动补 appId（wechatOrder/createCMBOrder 分支）、`requestNew` 无 webRoot 前缀签名（本项目无对应实现）。
- 注意：老项目自动注入 `appId` / `netUserId`，本项目只注入 `centerId`(Pinia appStore) / `tenantId`(storage)。调微信下单类接口需显式传 appId。
