## 补修：Pinia 持久化字段名

`stores/app.ts` 的 `persist.paths` → `pick`（v4 字段名，`paths` 被静默忽略）。两个 store 的 persist 块已拉平成同一套写法（key + pick + 同款注释）。

**⚠️ 修正上一轮的判断**：我曾说"paths 被忽略 → envConfig（含 apiSecret）被写进 Storage"，实测证明是错的。pinia 只把 ref/reactive 放进 `$state`，`envConfig` 是普通冻结对象，根本不进 `$state`，所以从来不会被持久化。用真实插件跑对照实验，`paths` 与 `pick` 写进 Storage 的 payload 完全一致。

真实影响降级为：**护栏失效**。写成 `paths` 等于没有任何过滤，当前恰好只有两个 state 字段所以无症状；后续往 store 加 ref（缓存/定位/草稿）会被静默全量持久化，没有任何东西拦着。

## 清掉双 px→rpx 机制：删除 manifest 的 transformPx

结论先行：**`transformPx` 在 Vue3 + Vite CLI 工具链下是死配置**，全量 grep `node_modules/` 零命中，没有任何编译器读它。已从 `src/manifest.json` 删除，保留自写 `pxToRpxPlugin`。

实证（同一份源码，只改变量）：
- mp-weixin：transformPx=true / false 两次构建，全部 `.wxss` 拼接 sha1 **完全一致**（`4f7f740b…`）；删字段后重建，仍是同一个 sha1。
- h5：同样 true/false 两次构建 sha1 一致（`befd5a6a…`）。
- 反证：transformPx=true + 摘掉自写插件 → 产物 0 个 rpx、2038 个 px，即框架侧完全不会兜底。

附带确认：H5 侧 uni 会把 rpx 编译成 rem（`.fz-40{font-size:1.25rem}`，1rem=32rpx），所以"px→rpx→rem"这条链路在 H5 也是响应式的，自写插件同时服务小程序与 H5。

自写插件已知瑕疵（本次未改，仅记录）：无差别处理 node_modules（`iconfont.css` 的 `font-size:16px` 被转成 16rpx≈8px，当前所有用点都显式设了字号所以未暴露）；正则直接作用于 `decl.value`，`url(xxx-16px.png)` 这类资源名会被误改（当前仓库无此命名）；不处理 `@media` 条件里的 px；大写 `PX` 不转；`0.5px` 会被转成 0.5rpx（≈0.25px，几乎消失）。
